What SavitriBridge is

SavitriBridge is a standalone Web Push notification and engagement platform. It is not tied to any one website: any number of external sites ("projects") can integrate the reusable browser client and receive real push notifications sent from this dashboard. Savitri Livings is simply the first project connected to it.

The platform has three parts: this admin dashboard (what you are using now), a backend API (Node.js/Express + MongoDB) that stores data and talks to browser push services, and a small browser client + Service Worker that any website copies in to receive notifications.

Key concepts

Subscriber
One browser/device that registered for push on a project's website. Identified by a SUB_... id, not a person — the same person on two devices is two subscribers.
Push subscription
The actual browser credential (endpoint + encryption keys) behind a subscriber. A subscriber can hold more than one over time (e.g. after clearing site data).
Attempt / Accepted
An attempt is the backend trying to send. Accepted means the push service (Google/Mozilla/Apple's infrastructure) took the message — not proof it reached or was shown on the device. Web Push has no delivery receipt.
Click
The Service Worker reports a click using a signed token embedded in the push payload. Opens/impressions cannot be measured with Web Push — only attempts, accepted, and clicks are real numbers.
Public project ID
A non-secret identifier (pk_...) a website uses to register subscribers. Safety comes from allowed origins + rate limiting + tokens, not from keeping this secret.

Architecture

Website (any project)→push-client.js + Service Worker→SavitriBridge public API→MongoDB Atlas
Admin dashboard→SavitriBridge admin API→web-push (VAPID)→Browser push service→Visitor's device

Frontend: vanilla HTML/CSS/JS, no build step, deploys as static files (e.g. Vercel). Backend: Node/Express + Mongoose on MongoDB Atlas (e.g. Render). Media: Cloudinary. Reverse geocoding: OpenStreetMap Nominatim (rate-limited, cached).

Admin roles

RoleCan do
SUPER_ADMINEverything, including managing other admins.
ADMINProjects, subscribers, campaigns, templates, analytics, logs. Cannot manage admins.
MARKETERCampaigns, templates, media uploads, analytics. Cannot manage projects/subscribers/admins.
VIEWERRead-only: dashboards, analytics, logs.

Roles are enforced on the backend (not just hidden buttons). Changing a role or deactivating an admin signs that admin out immediately everywhere.

Projects

A project represents one website. Allowed origins control which pages may register subscribers and which target URLs a campaign for that project may point to — this is the main safety boundary against open redirects and cross-site abuse. Deactivating a project stops new registrations but keeps existing subscribers intact.

Subscribers

The subscriber list shows device type, browser/OS, language, timezone, and — only if the visitor explicitly granted it — an approximate location. Disable stops platform-side sends without touching browser permission; Delete data removes push credentials and personal/device/location fields while keeping an anonymous shell so past campaign statistics stay accurate. Send test push sends a real transactional push to that one device.

Campaigns

Choose an audience (all active subscribers, one project's subscribers, or a single subscriber), write the notification, preview it, then Send now or Schedule — both require an explicit confirmation showing the estimated audience size. A campaign in PROCESSING is claimed atomically so it can never be sent twice, even if the server restarts mid-send (an interrupted send is marked FAILED for review rather than silently resent). Delivery attempts, per-subscriber results, and click tracking are all recorded.

Templates

Reusable notification content, global or scoped to one project. Starting a campaign from a template copies the content in so it can still be edited before sending; the template itself is unaffected.

Analytics

Every number is derived from stored delivery attempts and subscriber records for the selected date range and project — nothing is simulated. Click rate is tracked clicks ÷ accepted attempts, in the same period and filters. Location breakdowns only include subscribers who explicitly shared their location.

Logs & audit

The audit trail records who did what (created a campaign, changed a role, exported data, …). The failures log lists individual push delivery failures with a sanitised error category — raw endpoints, keys and tokens are never written to logs, exports, or the audit trail.

Security model

  • Admin sessions are short-lived JWTs; role or password changes invalidate every existing session for that admin.
  • Public endpoints are protected by origin allow-lists, input validation, rate limiting, and a per-subscriber proof token — CORS headers alone are never treated as authentication.
  • Campaign target URLs and uploaded media must be valid http(s) URLs, and target URLs must match the project's allowed origins — this blocks open redirects and script-injection via javascript: URLs.
  • Push endpoints and encryption keys are stored server-side, never returned by any API response, export, or log.
  • Click tracking uses a signed, per-send token generated at send time so click counts cannot be forged.

Privacy & data

Location is requested by the website, from a visitor's explicit action, and is never required for push to work. Address lookups use OpenStreetMap Nominatim (attribution: © OpenStreetMap contributors, ODbL) and are cached to limit repeat lookups for the same place. Deleting a subscriber's data removes personal fields immediately but keeps anonymous historical campaign statistics.

Deployment

  1. Create a MongoDB Atlas cluster and a Cloudinary account.
  2. Backend: deploy /backend (e.g. Render). Set every variable from .env.example. Run npm run generate-vapid once and store the keys — never regenerate them later, or every existing browser subscription breaks.
  3. Frontend: deploy /frontend as a static site (e.g. Vercel). Edit js/config.js to point at the deployed backend URL.
  4. Set FRONTEND_URL on the backend to the deployed dashboard origin(s).
  5. Sign in with the INITIAL_ADMIN_EMAIL / INITIAL_ADMIN_PASSWORD you set, then change the password immediately.
  6. Create a project per website, add its allowed origins, and follow the Integration page.

Troubleshooting

  • No push arrives but the campaign shows "Accepted" — expected sometimes: the device may be offline, in battery saver, or the OS suppressed it. Accepted is not a delivery guarantee.
  • ORIGIN_NOT_ALLOWED — add the exact page origin to the project's allowed origins.
  • CLOUDINARY_NOT_CONFIGURED on upload — paste a public HTTPS image URL instead, or configure Cloudinary env vars.
  • A campaign is stuck in PROCESSING — the scheduler marks any campaign interrupted for 30+ minutes as FAILED on the next backend restart, rather than risk a duplicate send.
