Web Push integration overview

A website loads push-client.js and its Service Worker. When a visitor clicks “Enable notifications”, the browser creates a PushSubscription which the client registers with the SavitriBridge public API using the public project ID. Campaigns are then sent from the dashboard; the browser vendor’s push service delivers them to the visitor’s browser.

Website→push-client.js→Service Worker→PushSubscription→SavitriBridge API→MongoDB

Project configuration

The public project ID and VAPID public key are not secrets. Security comes from allowed origins, validation, rate limiting and per-subscriber tokens; CORS alone is never treated as authentication.

Service Worker integration

Two service workers with the same scope conflict. If a site already has one, merge the push listeners rather than registering another.

Optional location

Never request location on page load. It is separate from notification permission and geocoded server-side with OpenStreetMap Nominatim.

Testing

  1. Add your site origin (e.g. http://localhost:5500 for development) to the project’s allowed origins.
  2. Open the Demo page or your site, click Enable notifications.
  3. Find the subscriber under Subscribers and choose Send test push.

Web Push needs HTTPS (localhost is exempt). On iOS it works only for sites added to the Home Screen (iOS/iPadOS 16.4+).

Allowed origins & troubleshooting

  • 403 ORIGIN_NOT_ALLOWED → the page origin (scheme + host + port) is not in the project’s allowed origins.
  • Permission “denied” → the user must re-allow notifications in browser site settings; the platform cannot override it.
  • No notification but “accepted” → the device may be offline, in battery saver, or notifications are blocked at OS level. Accepted ≠ delivered.
  • AUTH_VAPID_MISMATCH → VAPID keys changed after subscribing; users must re-subscribe.
