# Future integration: server-to-server API and Salesforce Marketing Cloud

**Status: not implemented in v1.** The route `POST /api/v1/integration/*` currently returns `501 NOT_IMPLEMENTED`.
This document records the intended design so a later version can build it without redesigning the data model.

## Why this is separate from the public API

The public API (`/api/v1/public/*`) is meant to be called from a browser: it is origin-restricted, rate-limited,
and every write is scoped to one subscriber via a proof token. It deliberately cannot "send to anyone" or read
platform-wide data.

A server-to-server integration (Savitri's own backend, or Salesforce Marketing Cloud) needs different things:
it is trusted, but it runs outside a browser and must never expose a VAPID private key or a database credential
to the browser. It needs its own credential type and its own route family.

## Planned shape

- **Auth**: a long-lived API key per external system, generated by a Super Admin, stored hashed (never logged, never
  returned after creation), sent as `Authorization: Bearer sk_live_...` and checked against the `integration` route
  prefix only — never accepted on `/api/v1/admin/*` or `/api/v1/public/*`.
- **Scope**: each key is scoped to one or more projects, mirroring the `Project.allowedOrigins` model already used
  for browser integration, so a leaked integration key cannot reach every project.
- **Endpoints (draft)**:
  - `POST /api/v1/integration/send` — trigger a transactional push for one `subscriberId` or a small explicit list,
    reusing `campaignService.prepareContent` / `sendNow` so validation, click tracking and delivery-attempt logging
    stay identical to dashboard-sent campaigns.
  - `GET /api/v1/integration/subscribers/:subscriberId/status` — read-only status check.
  - `POST /api/v1/integration/events` — optional inbound webhook for order/CRM events that should trigger a
    templated push (e.g. "order shipped").
- **Idempotency**: every write accepts an `externalRef` and stores it on the created `Campaign`/`DeliveryAttempt` so
  retried webhook deliveries don't double-send.
- **Salesforce Marketing Cloud**: SFMC would call `POST /api/v1/integration/send` from a Journey Builder Activity
  or a Cloud Page, using a per-org API key. No SFMC-specific code belongs in SavitriBridge itself — SFMC is just
  another caller of the same integration API.

## What NOT to change to build this

The audience model (`ALL_ACTIVE` / `PROJECT` / `SUBSCRIBER`), `Campaign`/`DeliveryAttempt` schemas, and
`pushService.sendCampaign` batching/retry logic are all reused as-is. Only a new auth middleware, a new key model,
and a new thin route/controller layer are needed.
